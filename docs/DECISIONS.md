### 2026-07-25 — Challenge layer: a "hold still while the light passes" tense encounter

**Rationale:** Issue #10 required picking one concrete form for the "light/stylized challenge layer" (already decided against a full battle system, see the 2026-07-25 combat entry above) by building it, not designing it on paper. Considered against the alternatives it explicitly named: an environmental puzzle (arranging/matching objects) felt more like a discrete minigame bolted onto the world than something that could recur naturally across future content without feeling repetitive; a "simple non-lethal confrontation minigame" risked drifting back toward stats/turns/a mini battle-system in practice, exactly what issue #4 was closed to avoid. A tense/stealth-style encounter won because it could be built as pure atmosphere with no numbers at all, and because it could directly pay off dialogue that already existed rather than inventing new lore: cairn_npc already says "some say lights move up there at night" (written in #8/#9, before this mechanic existed) - so the encounter *is* that light, made interactive, without the game ever confirming what it actually is. That directly matches the "grounded world, mythic edges" pillar (`docs/PROJECT_VISION.md`) - myth stays belief, never confirmed.

Concrete mechanic: approaching the cairn past cairn_npc, a wisp appears; the player must not move for 3 seconds while it drifts past. Moving during that window "fails" (a startled flinch, gently pushed back a couple of tiles, freely retryable); holding still "succeeds" once, permanently (sets a WorldState flag, no re-trigger, no reward loop) - see `game/scripts/cairn_encounter.gd`.
**Consequences:** No stats, health, or currency anywhere in this system - failing costs nothing but a few seconds and a short walk back; succeeding grants nothing numeric, just a flag and an atmospheric line. This sets the template for future challenge-layer content: tension from a simple, legible rule (here, stillness) plus atmosphere, not mechanical depth. `game/scripts/player.gd` gained `force_move_to()` (a scripted reposition bypassing normal input) specifically to support the "pushed back" beat - reusable for any future challenge-layer content that needs the same kind of non-player-initiated movement.
**Status:** final for this prototype instance; the general pattern (legible rule + atmosphere + flag, no numbers) is intended to guide future challenge-layer content, not just this one encounter.

### 2026-07-25 — Map authoring tool: named regions in GDScript, not Tiled or Godot's TileMap editor

**Rationale:** Issue #9 explicitly left the tooling choice open ("Tiled... or directly in Godot's TileMap editor, whichever proves faster in practice"). Both assume an interactive GUI (Tiled's application, or Godot's editor's TileMap paint tools); this project is built by an AI coding agent operating headless/CLI-only, with no mouse/window-driven editing available. A third option fits that constraint without adding a new toolchain dependency (Tiled + a Godot Tiled-importer plugin) or needing GUI automation: hand-author the layout as named `Rect2i`/`Vector2i` constants (house footprints, doors, the pond) checked in a fixed priority order in `main.gd::_tile_for()`, still built into the `TileMapLayer` through the same runtime `TileSet`-construction approach the procedural version used. This satisfies the actual distinction issue #9 cares about - hand-placed, deliberate structure vs. algorithmic/random generation - without depending on tooling that can't be driven in this environment.
**Consequences:** No Tiled `.tmx`/`.tmj` files or importer plugin in this repo. Adding/editing structures means editing named constants and the `_tile_for()` priority chain in `game/scripts/main.gd`, not painting in an external tool. If a human collaborator with editor/GUI access joins later and Tiled or Godot's TileMap editor genuinely becomes faster for authoring larger content, revisit this - the current approach doesn't scale gracefully much past a handful of hand-placed structures.
**Status:** final for AI-agent-only authoring; revisit if a GUI-capable collaborator takes over map content work.

### 2026-07-25 — Web save persistence: no manual FS.syncfs() call needed on this Godot version

**Rationale:** Godot's web export historically needed a manual JavaScript `FS.syncfs()` call (via `JavaScriptBridge.eval`) to flush `user://` writes from the in-memory IDBFS to the browser's real IndexedDB before a page reload — issue #3 was written expecting this. It was implemented first, then tested against the actual exported web build with a real Playwright-driven page reload (not just the Godot editor). That call threw `ReferenceError: FS is not defined` — on this project's Godot 4.7, that global isn't reachable from `JavaScriptBridge.eval`'s context; it's wrapped inside the engine's internal `GodotFS`/`godot_js_os_fs_sync` binding instead. The manual sync call was then removed entirely and the same real-browser-reload test was re-run: the save persisted correctly with no manual sync code at all, meaning `FileAccess.close()` already handles this internally on web in this Godot version.
**Consequences:** `game/scripts/save_system.gd` has no web-specific sync code — `save_game()`/`load_game()` are plain `FileAccess` calls that work identically across platforms. If save persistence ever appears to silently fail on web again (e.g. after a Godot version upgrade), re-verify this specifically against a real browser reload of the exported build before assuming a manual sync call is the fix — don't re-add the old `FS.syncfs()` approach blind, since the global isn't even valid in this version's export.
**Status:** final for Godot 4.7; revisit if the Godot version changes.

### 2026-07-26 — Audio production: procedural synthesis, following the art precedent

**Rationale:** Issue #14 required checking the real constraint before committing to an audio direction, the same discipline the art-production revision established rather than assuming the original "royalty-free/AI music+SFX" plan was still executable. Checked directly: no AI audio-generation tool (no ElevenLabs/Stability Audio-equivalent access) is available in this environment, and neither is `sox` nor `ffmpeg` on this machine. What *is* available: `numpy` (already a project dependency via `tools/art`) plus Python's stdlib `wave` module, sufficient to synthesize waveforms (sine/square/triangle/noise), shape them with an ADSR envelope, and write standard PCM `.wav` files Godot imports natively. Offered the choice directly (procedural synthesis; researching curated free/CC0 packs, with actual downloading/license-clearing left to the user; an AI audio API requiring the user's own credentials), the user picked procedural synthesis — same reasoning as the art decision: no new dependency or credential, fully executable end-to-end without the user's involvement, consistent with the project's no-budget constraint.
**Consequences:** `tools/audio/` holds the synthesis tooling (`synth.py`) and per-asset generation scripts (`generate/`), mirroring `tools/art/`'s structure — a script produces a `.wav`, committed under `game/assets/audio/`, not hand-edited directly. The minimal working example (issue #14's requirement) is a two-note UI chime on dialogue-box-open (`tools/audio/generate/dialogue_open.py` → `game/assets/audio/sfx/dialogue_open.wav`, played by `dialogue_box.gd`). The approach's ceiling is real: convincing instrumental music or rich ambience is a much harder procedural target than simple UI SFX or noise-based ambience (wind, water) — expect this to stay SFX/ambience-focused rather than a full soundtrack solution, similar to how the art decision accepted a "craft ceiling" trade-off.
**Status:** final for as long as this project is built by an AI agent without audio-generation tool access; revisit immediately if that access ever becomes available (mirrors the art decision's status).

**Addendum 2026-07-26 — real web *release* export: initial testing showed total silence, but this did not hold up under further retesting.** Issue #14's third acceptance criterion required verifying the chosen approach actually plays audio in a real exported web build, not just in the editor. Verification method throughout: `godot --export-debug`/`--export-release` builds served locally, driven with Playwright/Chromium, with an `AudioNode.prototype.connect` shim tapping actual output energy (RMS) via an `AnalyserNode` — not just checking for console errors, which prove nothing about audibility.

First round of testing (roughly a dozen runs over about an hour, spanning headless and real headed Chromium, the full game and a minimal isolated autoplay-only scene, `playback_type` forced to both `Stream` and `Sample`) showed a clean, consistent split: the **debug** web export always played the dialogue-open chime correctly; the **release** export — the one `docs/deployment.md`'s redeploy process actually uses — was always completely silent, zero output energy, no console/page errors. JS-level instrumentation added directly into the exported `index.js` (tracing `Bus.create`/`setSend`/`connect`, the sample-playback lifecycle, and `SampleNodeBus.setVolume`'s gain values) showed every step of the pipeline succeeding correctly — correct gains (L=1, R=1), `_source.start()` genuinely invoked, Master correctly connected to `ctx.destination` — with no discernible break in the traced logic, yet the release build still measured zero output energy at the time. This closely resembled the open upstream bug `godotengine/godot#119026`/its (also open, unmerged) fix PR #119027, though that bug's stated trigger needs 2+ audio buses (this project only has the default Master bus) and applying the exact one-line fix from #119027 directly to the exported `index.js` made no difference — so the resemblance was circumstantial, not a confirmed match.

**Second round, after adding that JS instrumentation:** the exact same (and then a freshly re-exported, completely unpatched) release build started playing audio correctly and has done so reliably in every subsequent test — 26 consecutive successful runs across several batches, using the same real interaction path (title screen → move → talk to an NPC → dialogue opens → chime plays) against the real `--export-release` output, with no code changes to the game in between the failing and succeeding rounds. The failure could not be reproduced again despite trying. No conclusive root cause was found for the earlier failures — the leading candidate (not confirmed) is transient local machine/audio-subsystem state from the large number of Chromium instances launched in quick succession during the first testing round, rather than a deterministic Godot or project-specific bug.
**Consequences:** The honest state of this finding is: verified-working-now, with an unexplained episode of consistent failure earlier in the same session that did not recur despite substantial further testing. This is unsatisfying but shouldn't be dressed up as either "confirmed broken" (the 26/26 retest contradicts that) or "confirmed fine, nothing to see" (an hour of consistent, varied-condition failures isn't nothing). Practical takeaway for future sessions: if release-export audio ever appears silent again, retest with a fresh browser/machine state before assuming a code regression, and if it recurs, the JS-level tracing approach developed here (patching `console.log` calls directly into the exported `index.js`'s `Bus`/`SampleNode`/`SampleNodeBus` methods) is the fastest way to localize exactly where a real break occurs.
**Status:** currently verified working (release export plays audio reliably as of this session's later, larger retest); not treated as a fully closed/understood problem given the unexplained earlier failures. A genuine real-device/real-browser spot-check before any actual public release remains worthwhile due diligence regardless.

### 2026-07-26 — NPC dialogue: conditional dialogue_lines replaces a single fixed line

**Rationale:** Issue #20 populated Act 1's real cast (five new named NPCs in the village, plus Gunnar on the ship) and explicitly asked whether M1's NPC/dialogue pattern (`npc.gd`'s single `dialogue_text: String`, reactive variation handled by `main.gd` reaching in and overwriting an NPC's text on a flag change) still scaled, rather than assuming it did. It didn't cleanly: that approach already needed two special-cases for one NPC with one reactive line (`water_npc` in `_on_flag_changed()` *and* again in `_place_npcs()` for a continued save that bulk-restores `WorldState` without emitting `flag_changed`) - scaling that to six NPCs, several with their own reactive lines, would have meant many scattered, easy-to-miss special-cases across `main.gd` instead of each NPC owning its own reactivity.
**Consequences:** `npc.gd`'s `dialogue_text: String` became `dialogue_lines: Array` (plain `Array`, not `Array[Dictionary]` - see the code comment; Godot doesn't implicitly convert an untyped `Array` from a Dictionary literal into a strictly-typed one), an ordered list of `{"flag": String, "value": Variant, "text": String}` entries. `get_dialogue_text()` now resolves the first matching entry against `WorldState` live, on every call, rather than main.gd pre-computing and caching a value on the NPC. This let both of `water_npc`'s special-cases in `main.gd` be deleted outright - the data now describes its own reactivity instead of code reaching in to update it. The same pattern immediately proved out on a second, cross-NPC case: Thora's line changes once the player has met Hakon (`FLAG_MET_HAKON`), the same "one system's flag changes another NPC's behavior" demonstration issue #8 established, now confirmed to still hold with more NPCs and more lines.
**Status:** final; the model held with six NPCs and is expected to keep holding for #21/#22's further reactive content, since adding a new conditional line to any NPC is now a data change, not a new special-case in `main.gd`.

### 2026-07-26 — Hint text: an interim message rather than a quest-log entry, for the water_npc/key discoverability gap

**Rationale:** Issue #25 (found during #23's playtest) needed a decision on how the player discovers that `water_npc`, not Gunnar, is the very next step after meeting Hakon - the hint jumped straight to "Find Gunnar" with no mention of the key blocking the south gate. Of the options the issue itself raised (adjust the hint text, adjust an NPC's dialogue, or something else), adjusting `_update_hint()`'s `MET_HAKON` branch was the smallest change that fixed the actual gap: it now checks `GATE.is_unlocked()` and shows an interim "a rockslide still blocks the path south - ask around near the water" message until the player actually holds the key, rather than a new quest-log/journal entry, which stays out of scope until M4 per `docs/PROJECT_VISION.md`. An independent review of the first pass at this fix caught two things worth recording: the initial version checked `Inventory.has_item(GATE.required_item_id)` directly instead of `GATE.is_unlocked()`, which would have silently drifted out of sync with the actual gate state if `south_gate.tres` ever also gained a `required_flag` (the two checks only coincide today because it doesn't); and picking up the key doesn't change any `WorldState` flag, so `_on_item_added()` needed its own `_update_hint()` call - without it, the hint stayed on the old message until an unrelated flag change happened to refresh it.
**Consequences:** `game/scripts/main.gd`'s `_update_hint()` and `_on_item_added()` both changed; `game/scripts/ship.gd`'s mirrored `_update_hint()` deliberately does *not* gain the same branch, since reaching that scene at all already implies `GATE.is_unlocked()` is true (the gate is the only route from the village to the ship) - this is an implicit invariant, not enforced by any assertion, and would need revisiting if a second route to the ship or a second gate ever gets built. Re-verified end-to-end against a fresh `--export-release` build with the same Playwright-driven standard as issue #23: zero console errors, hint text correct at every step, correct through save/reload.
**Status:** final for this one gap; the underlying "no quest log until M4" constraint this works around is unchanged.

### 2026-07-26 — Web payload: no atlasing/lazy-loading built yet; a forward budget recorded instead

**Rationale:** Issue #27 required measuring the exported web build's payload (following `norse-game`'s documented methodology, not reinventing one) and either building atlasing/lazy-loading or recording why it isn't needed yet - the issue's own acceptance criteria explicitly allowed the latter. Measurement showed `index.pck` (all of this project's actual content: two areas, all NPCs/dialogue/items, one audio SFX) is 67,712 bytes - about 0.17% of the ~38 MiB total, completely dominated by the Godot engine binary (`index.wasm`, byte-identical to norse-game's own build on the same Godot version). Building atlasing/per-region-loading infrastructure against a 66 KB problem would be unneeded complexity for a constraint that doesn't exist yet, so none was built. The one real, previously-unstated fact worth recording instead: Godot's web export bundles the entire project into one `.pck` fetched upfront at boot - moving between the village and ship scenes frees/re-instantiates in-memory nodes but doesn't fetch new bytes over the network, so no per-region *network* lazy-loading exists today even though the scene-based architecture might look like it implies some.
**Consequences:** `docs/PERFORMANCE.md` (new) records the full measurement (raw sizes, gzip/brotli compression, simulated-network load times, and live verification against both actual hosts - GitHub Pages and itch.io both serve gzip but not brotli, same finding norse-game made for GitHub Pages alone) and a concrete forward budget: ~1-2 MB raw per region as a trigger point for actually building `ProjectSettings.load_resource_pack()`-based on-demand loading, not a hard limit in itself. Re-measure when M2's placeholder art/audio gets replaced with hand-tuned hero assets, when real music is added, or when region count approaches that budget cumulatively - whichever comes first.
**Status:** final for the current build; the budget is a forward trigger point, not a permanent number - expected to be revisited exactly once one of the stated triggers actually happens, not on a schedule.

### 2026-07-26 — Platform: web-only for now, no desktop build

**Rationale:** Issue #28 required deciding this directly with the user (per `docs/PROJECT_VISION.md`'s "What's not decided yet"), not assuming it. Presented as a tradeoff, not a binary yes/no: a downloadable desktop build (Windows/Mac/Linux, same Godot project, distributed via itch.io alongside the web version - no new tooling needed, `butler` already supports multi-channel uploads per issue #24) would give better performance (no ~38 MiB WASM floor per issue #27), offline play, and side-steps web-export limitations (single-threaded, no GDExtension support, per `docs/deployment.md`). Against that: this is a solo, no-cash-budget project, and an unsigned macOS build hits Gatekeeper warnings unless code-signed (Apple Developer Program, $99/year) - a real cash cost the project has avoided everywhere else (see the art/audio production-method decisions). It also adds a second platform to re-verify every release, on top of the substantial single-platform playtest issue #23 already required. Issue #27 also confirmed the web build's actual load time is already fine (~9s throttled, ~1s good connection) - there's no current technical problem a desktop build would be solving. The user asked for a recommendation weighing "major advantages" specifically, rather than a default yes; none of the upsides were judged major enough to outweigh the cash-cost and maintenance-surface downsides at this stage, so the recommendation was web-only, which the user confirmed.
**Consequences:** No desktop export/signing work done. `docs/PROJECT_VISION.md`'s "What's not decided yet" section updated to reflect this as decided, not open. Revisit only if a concrete trigger shows up later (players actually asking, a real technical wall on web, or the game reaching a scale where broader distribution matters more) - the same "defer until there's an actual reason" pattern already used for M7's mobile-ports question, not a permanent, un-revisitable no.
**Status:** final for now; explicitly revisitable given a concrete future trigger, not a schedule.

### 2026-07-26 — Cutscene/dialogue-scripting: a data-driven CutscenePlayer, proved out on the ship's memory beat

**Rationale:** Issue #31 needed a way to author a sequence of dialogue lines/camera moves/waits for larger story beats, since the existing dialogue system (`dialogue_box.gd`/`npc.gd`'s `dialogue_lines`) shows one line at a time on direct interaction only - Act 1's resolution beat and the challenge encounters are each hand-wired in `main.gd`/`ship.gd` today, which M5's story acts would otherwise have to keep repeating per beat. Modeled as an ordered Array of step Dictionaries (`{"type": "dialogue"/"wait"/"camera_pan"/"flag", ...}`), matching this project's established "plain data over bespoke code" discipline (`dialogue_lines`, `QuestLog._STEPS`, `NPC_PLACEMENTS`) rather than a scripting language or per-beat subclassing. Camera movement tweens `Camera2D.offset` (a relative offset Godot's Camera2D exposes specifically for this) rather than reparenting or moving the camera's position directly - the camera stays parented to Player exactly as before, so a cutscene's pan is just a temporary visual offset, not a change to how the camera actually follows the player.
**Consequences:** `game/scripts/cutscene_player.gd` (`class_name CutscenePlayer`) is a plain Node (one instance per scene that needs it, mirrored rather than shared/autoloaded - matching this project's existing `_transition_to()`-style mirroring precedent), wired via `initialize(dialogue_box, camera, player, closeable_panels)` and driven by `play(steps)`/`advance()`/`is_playing()`. Proved out end-to-end by reworking ship.gd's memory-encounter-succeeded beat (issue #21) from a single static `_dialogue.open(...)` line into a real sequence: set `QuestFlags.MEMORY_SURFACED` → a first line → a camera pan out over the water → a beat of silence → a second line (new content, consistent with `docs/WORLD_BIBLE.md`'s "never a confirmed monster" stance) → the camera pan back - verified against both the debug and release exported web builds via Playwright with zero console errors. An independent review caught a real soft-lock this introduced: `_process_interact()`/`_process_inventory_toggle()`/`_process_journal_toggle()`/`_process_map_toggle()` in `ship.gd` each check their own panel's `is_open()` before `_cutscene.is_playing()`, so if Inventory/Journal/the world map happened to already be open when the (purely spatial, UI-independent) memory encounter succeeded, the resulting cutscene dialogue could never be advanced (Space couldn't reach it) *and* the open panel could never be closed (its own toggle key saw a "cutscene playing" state first) - a genuine deadlock, not a hypothetical one, since I/J/M are global keys with no relationship to the encounter's own trigger position. Fixed by having `play()` force-close any panel from a passed-in `closeable_panels` list before starting, so a cutscene always begins from a clean, panel-free state regardless of what was open the instant its trigger fired.
**Status:** final for this one proved-out beat; the same `CutscenePlayer` step-array pattern is expected to extend to M5's later story beats via new step arrays, not a new per-beat mechanism. A known accepted limitation (not fixed): a reload in the narrow window after a cutscene's first "flag" step but before the sequence finishes permanently skips the rest of that specific cutscene (see the comment on cutscene_player.gd's "flag" step) - acceptable for the same reason other one-shot dialogue content in this project isn't reload-safe mid-beat either.

### 2026-07-26 — Accessibility pass: remappable input, text size, colourblind check, touch controls

**Rationale:** Issue #32 (M4's last item) required all four of docs/PROJECT_VISION.md's named accessibility pieces in one pass, none of which existed yet: all input was hardcoded to raw keycodes, text size was fixed, the palette had never been checked against colour-vision deficiency, and there were no touch controls despite the web platform including mobile browsers.

**Remappable input:** Godot's own `InputMap` is the idiomatic mechanism for this, so `player.gd`/`main.gd`/`ship.gd` were refactored from `Input.is_key_pressed(KEY_X)` to `Input.is_action_pressed("move_up")` etc., with a new `Settings` autoload (`game/scripts/settings.gd`) building these actions at runtime rather than via `project.godot`'s static `[input]` section (which intentionally defines none of them). Each action gets exactly one remappable "primary" key plus fixed alias keys (WASD, Enter) that remapping never touches, so a player who never opens Settings keeps today's exact layout. A new `settings_screen.tscn`/`.gd`, reachable from a new "Settings" button on the title screen (before any save exists, since key bindings are a device/player preference, not save-scoped), lists every action from `Settings.get_actions()` and lets the player rebind by clicking then pressing a key. Persisted to a separate `user://settings.json`, not merged into `SaveSystem`'s save file.
**Text size:** `Settings.get_text_scale()`/`scaled_font_size()` (80%-160%, adjustable from the same settings screen), applied via `add_theme_font_size_override()` in `dialogue_box.gd`, `inventory_ui.gd`, `journal_ui.gd`, and the Hint labels in `main.gd`/`ship.gd`. The Hint's control-scheme text is now built live from `Settings.controls_hint_text()` instead of a hardcoded string - a static "I for inventory" string would go stale/misleading the moment remapping is actually used.
**Colourblind check:** `tools/art/colorblind_check.py` simulates protanopia/deuteranopia/tritanopia (Brettel/Vienot-derived matrices, the same family behind common open-source simulators like Coblis - not clinically validated, but a real checkable heuristic) against the pairs that actually matter for play - walkable tiles (grass/path) vs. blocking ones (water/wall/roof), with the south gate's own path/wall distinction as the highest-stakes single case. Full findings and the resulting `Stone`/`Timber` ramp revision are recorded in `docs/ART_BIBLE.md`'s new "Colourblind-safety check" section rather than duplicated here.
**Touch controls:** `game/scripts/touch_controls.gd` + `touch_controls.tscn` - a D-pad and one interact button, shown only when `DisplayServer.is_touchscreen_available()` is true, driving the exact same input actions via `Input.action_press()`/`action_release()` so `player.gd`/`main.gd`/`ship.gd` never branch on input source.

**Consequences:** An independent review of the first pass caught two real problems, both fixed before this shipped. First, rebinding had no collision detection - rebinding any action onto a key already used by another action's primary or fixed alias silently created a dead/double-firing key (e.g. rebinding `interact` onto `W` would make every `W` press both talk and walk) with no warning. Fixed by `Settings.find_conflicting_action()`, checked in `settings_screen.gd` before applying a rebind; a conflicting attempt now shows "In use by <action>" for a beat and reverts, rather than either applying it or silently doing nothing. Second, the text-scale font overrides were applied to Panels sized for the fixed 16px baseline with no room to grow - confirmed empirically (not just reasoned about) that one of Hakon's real dialogue lines at max (160%) scale spilled its third wrapped row out past `DialogueBox`'s own border. Fixed two ways: `DialogueBox` now grows its panel height proportionally with `Settings.get_text_scale()` (tuned against that same real line until all three wrapped rows fit, verified via a fresh screenshot), while keeping the default 100%-scale panel size byte-identical to before; `InventoryUI` gained a `ScrollContainer` mirroring `JournalUI`'s own (issue #29 solved this identical "a list can outgrow a fixed panel" problem already - reused, not reinvented). The Hint label was left as-is: it has no Panel/background behind it, so text extending further down over the game view at high scale isn't a rendering bug, just more of the screen covered by bigger text - an accepted, inherent trade-off of the feature, confirmed to look clean at 140% scale during testing.
**Verification:** All four pieces verified against both the debug and release exported web builds via Playwright - the full Act 1 walkthrough plus world-map/cutscene regressions still pass after the input-action refactor; rebinding, conflict rejection, and text-scale persistence (including across a real browser reload with zero save game ever created) all confirmed; touch controls confirmed using Playwright's mobile-device/touch emulation (iPhone 13 profile, `hasTouch: true`) - stated plainly, this is emulated touch dispatch in Chromium, not a physical device test, since none is available in this environment; a held (not instantaneous) press was needed to reliably register a move, matching real finger-press timing rather than a synthetic instant tap.
**Status:** final for this pass; touch controls deliberately cover only movement/interact per the issue's "basic" wording - Inventory/Journal/the world map remain keyboard-only until a later issue actually needs them on touch.

### 2026-07-26 — World map/fast travel: a data-driven AreaRegistry replaces the two hand-kept-in-sync entry-cell constants

**Rationale:** Issue #30 needed a world map showing visited areas and fast travel between them, built so M5 can register new regions without rearchitecting. main.gd and ship.gd already each hardcoded the *other* scene's arrival point locally (`SHIP_ENTRY_CELL` in main.gd, `VILLAGE_ENTRY_CELL` in ship.gd), with a comment on each flagging that they had to be kept in sync by hand and pointing at this exact file: "see docs/DECISIONS.md if a third area makes that worth building" (from the issue #19 area-transition entry). Fast travel is that third consumer - it has to resolve *any* visited area's scene path/arrival point generically, not just "the other one of exactly two scenes," so a real lookup table was built instead of a third hand-duplicated copy of the same coordinates. This follows the same "centralize a name/value the moment a second-or-later consumer needs it, not before" precedent as `quest_flags.gd` (see the issue #21/#29 entries above).
**Consequences:** `game/scripts/area_registry.gd` (`class_name AreaRegistry`) holds one `AREAS` array of `{id, display_name, scene_path, entry_cell}` dicts - currently `village` and `ship`. Both `main.gd`'s `_on_player_moved()` → ship transition and `ship.gd`'s → village transition now resolve through `AreaRegistry.get_area()` via a shared `_transition_to_area()` helper (mirrored in both scripts, not shared, matching this project's existing `_transition_to()` mirroring precedent) instead of their own locally-hardcoded entry-cell constants, which were deleted. A new `WorldMap` autoload (`game/scripts/world_map.gd`) mirrors `Inventory`'s held-items-set pattern for a set of visited area ids, persisted through the same save-dict merge (`world_map` key) `flags`/`inventory` already use; `title_screen.gd`'s Start (new game) now also calls `WorldMap.clear()` alongside `WorldState.clear()`/`Inventory.clear()`, so a fresh game in the same browser session doesn't inherit a previous playthrough's visited areas. `WorldMapUI` (`game/scripts/world_map_ui.gd`) mirrors `InventoryUI`/`JournalUI`'s open/close/refresh shape but builds one `Button` per visited area instead of a text `Label`, since fast travel needs an action per row, not just information; areas never visited are omitted entirely rather than shown locked, and the current area shows as a disabled "(you are here)" row. Adding a future area (M5) means one new `AREAS` entry, one `WorldMap.mark_visited()` call in that scene's `_ready()`, and picking one arrival cell - no other code changes, per `area_registry.gd`'s own header comment.
**Status:** final for Act 1's two areas; the same `AreaRegistry`/`WorldMap` pattern is expected to extend to M5's later regions by adding entries to the existing data, not by inventing a new mechanism per region.

### 2026-07-26 — Quest log: coexists with the hint line; a shared QuestLog replaces two duplicated hint implementations

**Rationale:** Issue #29 required deciding whether the new journal panel replaces the existing trailing-hint-line (`_update_hint()`, see the issue #21/#25 entries above) or the two coexist. Chose coexist: the hint stays for at-a-glance "what to do next" without opening a panel, matching this project's "exploration first, minimal friction" design pillar (`docs/PROJECT_VISION.md`); the journal adds the history-of-completed-beats and discovered-secrets record the hint was never meant to carry. Building the journal also meant main.gd and ship.gd's two separately-maintained `_update_hint()` implementations needed a real single source of truth rather than a third copy of the same logic - both now call a new `game/scripts/quest_log.gd` (`class_name QuestLog`, not an autoload, since it holds no mutable state of its own - a data-driven ordered step list, same style as `dialogue_lines`/`GateDefinition`, not executable callables). This directly resolves the implicit invariant issue #25's entry flagged (ship.gd previously couldn't mirror main.gd's gate-check branch and relied on unenforced reasoning about why that was safe) - both scripts now call the exact same function, so there's nothing left to keep in sync by hand.
**Consequences:** An independent review of the first pass at `QuestLog.get_current_objective()` caught a real regression before this shipped: a naive forward scan for "the first not-yet-done step" breaks once steps can complete out of order, which they can here - `ship.gd`'s memory encounter is deliberately reachable without ever setting `TALKED_TO_GUNNAR` (see that file's own comment), and `main.gd` sets `ACT_ONE_RESOLVED` off `MEMORY_SURFACED` alone with no check on `TALKED_TO_GUNNAR`. In that reachable state a forward scan would show "Find Gunnar..." forever, even after Act 1 has actually resolved. Fixed by scanning backward for the highest-progressed done step instead, matching what the original per-script `_update_hint()` implementations actually did (checking `ACT_ONE_RESOLVED` before `MEMORY_SURFACED` before `TALKED_TO_GUNNAR`, most-progressed-first) - `get_completed_steps()` (the journal's own "So far" list) didn't need the same fix, since an unordered record of what's actually happened is correct as-is, unlike a single "next objective" line. Two flag constants (`asked_about_cairn`, `cairn_light_passed`) moved from local consts in `main.gd` into the shared `quest_flags.gd`, since `quest_log.gd` became a second consumer needing the same names (see that file's own updated comment for why this mirrors the project's existing "centralize on the second consumer" precedent). The journal panel itself needed a `ScrollContainer` (not just a bigger fixed panel) after manual verification found Act 1's full completed-steps-plus-secrets text overflows any reasonably-sized fixed panel by the final beat.
**Status:** final for Act 1's scope; the same `QuestLog`/journal pattern is expected to extend to M5's later acts by adding steps/secrets to the existing data, not by inventing a new mechanism per act.
